# Research schema

`research.json` uses schema version 1 and contains `project`, `sources`,
`concepts`, `claims`, and `relations` arrays plus timestamps.

## Source

Every source has a stable content-derived ID, original filename and absolute
input path, SHA-256, format, extraction method, word/token estimates, nullable
bibliographic metadata, extracted-text and metadata paths, ingestion timestamps,
and incremental compilation fields. Unknown bibliographic metadata stays `null`;
it is never inferred during ingestion.

## Claim and evidence

A claim requires `id`, `text`, and an origin from `author`, `external`, `mixed`,
or `uncertain`. `source_ids` and `concept_ids` are references. Confidence, when
present, is between zero and one.

Origin semantics are:

- `author`: the claim is attributed to the research author.
- `external`: the claim is attributed to cited scholarship or external evidence.
- `mixed`: the claim is an explicit synthesis that cannot be attributed to one
  direct source claim, especially when it combines author and external material,
  integrates multiple provenance classes, or constructs a documented diachronic
  synthesis such as a concept's evolution. Multiple sources alone never justify
  `mixed`; the synthesized content and provenance boundary must be explicit.
- `uncertain`: the available evidence cannot support a firmer attribution.

Evidence records contain a `source_id`, nullable page/section/paragraph locator,
nullable quote, summary, and one of `explicit`, `inferred`, `supporting`, or
`contradicting`. Quotes must be source text, never model reconstructions.

Locator validation checks portable structural constraints: pages are positive
integers, section and paragraph values are non-empty strings when present, a
locator object is not entirely empty, and its evidence source belongs to the
claim's `source_ids`. It does not claim to verify that a printed page or section
contains the cited passage; that still requires source-text review.

## Concept evolution

A concept stores an ID and append-only `versions`. Each version has a source ID,
date (nullable when unknown), and definition. The current canonical definition
may synthesize versions but must not delete them. Concept Markdown files should
include canonical definition, alternatives, first appearance, evolution, related
concepts, supporting claims, and sources.

## Canonical and derived records

`research.json` is the single source of truth for the concept registry, claim
registry, every `claim.concept_ids` relationship, and semantic `relations`.
Concept Markdown, claim JSON files under `claims/`, and `topic-index.md` are
derived retrieval views. They must never be used to overwrite canonical
relationships. Run `research-to-skill sync-artifacts --project <path>` to
regenerate their relationship fields from the manifest.

Validation reports a warning when a derived concept or topic index is merely
stale or incomplete. It reports an error when a derived artifact asserts a
non-canonical relationship, references a nonexistent claim, or when a claim
artifact's `concept_ids` differs from the manifest. This distinction allows safe
regeneration for omissions while preventing invalid relationships from being
silently accepted.

## Graph

`relations/knowledge-graph.json` has `nodes` and `edges`. Node types are
`concept`, `claim`, `source`, `author`, and `publication`. Edge types are
`defines`, `supports`, `contradicts`, `extends`, `revises`, `cites`,
`derived_from`, and `related_to`. Both ends of every edge must exist.

`claim.concept_ids` records canonical claim-to-concept membership, but it does
not determine whether a graph edge should be `defines`, `supports`, `revises`,
or another semantic type. A graph edge must not be generated by guessing that
type. Existing typed relations remain canonical in `research.json`.

Publication author, year, and DOI values currently also appear in publication
nodes, paper views, and the bibliography. Consolidating that bibliographic
metadata and its evidence is deferred to the Phase 2B metadata adapter.

## Migration policy

Readers reject unknown schema versions rather than silently reinterpret data.
Future migrations should be explicit, one version at a time, preserve a backup,
and never change stable source IDs or hashes.

During compilation, the host writes a transient `semantic-results.json` object
with `concepts`, `claims`, and `relations` arrays. `compile --complete` validates
and merges those arrays into `research.json`, removes the successfully consumed
proposal to prevent stale replay, and synchronizes derived retrieval views while
the writer lock is still held. The proposal is never canonical.
